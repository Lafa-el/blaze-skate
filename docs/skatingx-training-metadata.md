# SkatingX Training Metadata Layer

Date: 2026-06-19

## Current `profile/main` Model

Blaze Skate Training still stores all user-owned Training data in one Firestore document:

```text
artifacts/blaze-skate-production/users/{uid}/profile/main
```

This path remains unchanged. Sprint 1 does not move collections, split the profile document, or migrate historical records.

## Metadata Fields

New and updated `profile/main` writes now include a small SkatingX compatibility metadata layer:

```text
ownerUid
sourceApp
schemaVersion
createdAt
updatedAt
```

Current values:

```text
sourceApp = blaze-skate-training
profile schemaVersion = skatingx-athlete-v1
training schemaVersion = skatingx-training-v1
```

`ownerUid` is the Firebase Auth uid used in the existing Firestore path. `createdAt` and `updatedAt` are ISO timestamp strings generated by the client repository layer.

## Compatibility Strategy

Historical `profile/main` documents may not have metadata. They continue loading through the same snapshot subscription.

When metadata is missing, the repository injects default metadata in memory before passing data to the React app. This avoids a forced migration and keeps existing rendering logic working.

On the next normal profile write, the repository refreshes:

```text
updatedAt
sourceApp
schemaVersion
ownerUid
```

If the profile is being created for the first time, it also writes `createdAt`.

## Validation

All repository write paths require a real Firebase uid before creating a profile document reference. This keeps writes tied to the existing Auth-owned document path and avoids fallback IDs.

## Future Migration Path

SkatingX Core integration should remain deferred until a dedicated migration sprint. The likely future path is:

1. Keep `profile/main` as the legacy source of truth while metadata adoption stabilizes.
2. Add tests around Training task, record, points, and rollover behavior.
3. Design Core collections for users, athletes, training records, gamification, and settings.
4. Build a migration script that can split `profile/main` into Core documents.
5. Add legacy read fallback before switching production rendering to the Core schema.

This sprint only prepares documents for future ownership and schema detection. It does not change the current data model.
